   258→   258→## CORE GENEALOGY FOUNDATION — IMPROVEMENT AREAS IDENTIFIED
   259→   259→
   260→   260→### TIER 1: Critical Foundation Gaps
   261→   261→
   262→   262→**F-1. No distinction between 'blood lineage' and 'married-in spouse' in data model**
   263→   263→- Current: All persons are treated identically. The system cannot distinguish between a Hariandja blood member and a spouse who married in.
   264→   264→- Impact: Tree root filtering (fixed above) is a workaround, not a solution. The fundamental issue remains that the data model doesn't encode this critical Batak Toba genealogy concept.
   265→   265→- Recommendation: Add a `is_blood_lineage` (BOOLEAN DEFAULT 1) or `lineage_type` ('blood' | 'married_in') column to persons. When creating a partnership, the non-Hariandja spouse should be marked as 'married_in'. This enables: correct tree root selection, lineage-specific statistics, and proper GEDCOM export.
   266→   266→
   267→   267→**F-2. No audit trail / change history**
   268→   268→- Current: All mutations (person update, partnership create/delete) are permanent with no history tracking.
   269→   269→- Impact: For a genealogy application, data accuracy is critical. Accidental deletions or incorrect edits cannot be undone. There's no way to see who changed what and when.
   270→   270→- Recommendation: Add an `audit_log` table (id, user_id, action, entity_type, entity_id, old_values JSON, new_values JSON, created_at). Record all CUD operations. Consider soft-delete for persons instead of hard-delete.
   271→   271→
   272→   272→**F-3. No data backup / GEDCOM export-import**
   273→   273→- Current: Only visual exports (PNG/JPG/PDF) exist. No structured data export.
   274→   274→- Impact: If the SQLite database is lost, all genealogy data is permanently gone. No way to migrate data to/from other genealogy tools.
   275→   275→- Recommendation: Implement JSON backup export/import endpoint. Consider GEDCOM 5.5.1 standard support for interoperability with other genealogy software (Ahnenblatt, Gramps, FamilySearch).
   276→   276→
   277→   277→### TIER 2: Important Functional Gaps
   278→   278→
   279→   279→**F-4. No cycle detection beyond direct self-reference**
   280→   280→- Current: parent_child has CHECK(parent_id != child_id) preventing A→A, but nothing prevents A→B→C→A cycles.
   281→   281→- Impact: If cycles are introduced (via API bug or direct DB manipulation), the tree rendering uses a `visited` set to prevent infinite loops, but the data would be semantically corrupt and the tree would silently drop nodes.
   282→   282→- Recommendation: Add recursive cycle detection in updatePerson/createPerson before inserting parent_child links. Walk up the ancestor chain from the proposed parent to verify the child doesn't appear.
   283→   283→
   284→   284→**F-5. Generation number only auto-calculated from father**
   285→   285→- Current: POST /api/persons calculates nomor_generasi from father only. If only mother is specified, the user must manually set generation.
   286→   286→- Impact: Children with only a mother recorded get generation 1 by default, regardless of the mother's actual generation.
   287→   287→- Recommendation: Also check mother's generation as fallback. Use MAX(father_gen, mother_gen) + 1 if both parents are specified.
   288→   288→
   289→   289→**F-6. Limited search scope**
   290→   290→- Current: searchPersons() only queries `nama LIKE ? OR nama_panggilan LIKE ?`.
   291→   291→- Impact: Cannot search by birth place, address, phone, religion, generation number, or burial location. For large families, users need more filter dimensions.
   292→   292→- Recommendation: Extend search to include tempat_lahir, alamat, agama. Add a dedicated filter/search API with structured parameters (generation, gender, marital status, date ranges) instead of just a text search.
   293→   293→
   294→   294→**F-7. Deceased/divorced spouses disappear from tree**
   295→   295→- Current: spouseMap in getTreeData() only includes partnerships where divorce_date IS NULL. When a person dies (auto-divorce sets divorce_date), the spouse completely disappears from the tree. When a couple divorces, same result.
   296→   296→- Impact: The tree loses historical context. In Batak genealogy, knowing who was married to whom (even if divorced or deceased) is important.
   297→   297→- Recommendation: Show ALL spouses in the tree with visual distinction: solid line for active, dashed line for divorced, cross/overlay for deceased. This requires extending spouseMap to include divorced/deceased partnerships.

   299→   299→**F-8. No sibling relationship concept**
   300→   300→- Current: Siblings can be inferred (shared parents) but there's no first-class sibling query or display.
   301→   301→- Impact: Person detail shows parents and children but not siblings. Users must navigate to parent's detail to see other children.
   302→   302→- Recommendation: Add getSiblingOf(personId) query. Show siblings section in PersonDetail. Consider sibling order (by birth date or nomor_urut_lahir).

   306→   306→**F-9. Missing Batak-specific fields**
   307→   307→- No `marga` field per person (currently hardcoded 'Hariandja' in tree subtitle). If the app ever expands to multi-marga, every person needs their own marga.
   308→   308→- No `tempat_meninggal` (place of death) — only date is tracked.
   309→   309→- No `marriage_place` in partnerships.
   310→   310→- No `photo` upload mechanism — the field exists but there's no upload endpoint or UI.
   311→   311→- No `notes` or `biography` field for additional context.
   312→   312→
   313→   313→**F-10. No date validation logic**
   314→   314→- Current: Dates are stored as free-form strings. No validation that: birth date < death date, marriage date < divorce date, child birth date > parent birth date, etc.
   315→   315→- Impact: Nonsensical dates can be stored (e.g., death before birth, child born before parent).
   316→   316→- Recommendation: Add date validation in API routes. At minimum: death_date >= birth_date, marriage_date <= divorce_date.
   317→   317→
   318→   318→**F-11. No statistics/dashboard**
   319→   319→- Current: No way to see aggregate family statistics (total members per generation, male/female ratio, deceased count, marital status distribution, oldest living member, etc.).
   320→   320→- Impact: For large families, statistical overview is valuable for understanding the family's composition.
   321→   321→- Recommendation: Add a statistics API endpoint and a dashboard panel with charts.
   322→   322→
   323→   323→**F-12. SQLite single-writer concurrency**
   324→   324→- Current: better-sqlite3 with WAL mode. Only one write transaction at a time.
   325→   325→- Impact: If multiple editors submit changes simultaneously, one will get SQLITE_BUSY error. For a single-family app this is unlikely but becomes an issue at scale.
   326→   326→- Recommendation: For current scale (single marga, ~hundreds of members), this is acceptable. Document the limitation. If scaling to multi-marga, consider PostgreSQL.
